# Non-Gameplay Refactor and Profiling Progress

## Goal

Improve future debugging, development, profiling, and performance work without changing default gameplay feel, visuals, audio, physics behavior, shader output, terrain edit behavior, or persisted runtime defaults.

Done means:

- Refactors are behavior-preserving and validated with the normal project checks.
- Profiling/logging improvements are opt-in or already-gated by existing `--perf`/diagnostics paths.
- Performance cleanups do not change visible gameplay/effects and are backed by release hidden-run logs where relevant.
- The codebase is easier to navigate, measure, and safely optimize in later passes.

## Current State

Known from repository inspection:

- Main app orchestration is concentrated in `src/app/core/mod.rs` (~3k lines), with frame loop, loading, UI panels, screenshot helpers, startup debug content, timing, and rendering orchestration interleaved.
- Water simulation is isolated in `crates/re-flora-water`, with the main hot file `crates/re-flora-water/src/mls_mpm.rs` (~3.9k lines). Existing docs identify G2P as the dominant water CPU cost.
- Water simulation runs on a dedicated worker through `src/app/core/water/runtime.rs`; main-thread `water_handoff` is not simulation compute time.
- Terrain visible rebuild policy is intentionally synchronous for visual correctness; async follow-up queues remain for terrain SDF/collider/water cache work. See `docs/terrain_visual_rebuild_pipeline.md`.
- GPU profiling exists in `re-flora-vkn` and is enabled by `--perf`. Current docs require no timestamp waits in measured frames and no profiler overhead when disabled.
- Perf logs already use stable markers such as `[PERF][FRAME]`, `[PERF][WATER]`, `[PERF][SYNC_VISIBLE_REBUILD]`, `[PERF][GPU_FRAME_SCOPE]`, and `[PERF][PARTICLES]`.
- Generated files exist under `src/auto-generated` and `src/app/generated`; do not hand-edit unless regenerated by build/check.
- `config/gui.toml` diffs after app runs are suspicious unless intentionally changing defaults.

## Plan / Phases

### Phase 1: App-core structure split

- Objective: Reduce `src/app/core/mod.rs` size and improve navigation by moving cohesive behavior into modules without logic changes.
- Expected output: Small modules such as loading, screenshots, startup debug setup, frame timing, and UI panel composition; imports adjusted; behavior unchanged.
- Dependencies/blockers: Need careful copy/move boundaries to avoid broad borrow/lifetime churn.
- Status: in progress; run-log helpers were extracted from `src/main.rs` into `src/run_log.rs` with pure unit tests.

### Phase 2: CPU timing/profiling helper

- Objective: Replace repeated manual `Instant` timing blocks with a small, opt-in timing helper that preserves existing log semantics.
- Expected output: Reusable scoped timing/timing-accumulator utilities for frame and queue timings, with disabled-path overhead kept minimal.
- Dependencies/blockers: Must not allocate or format strings when profiling/timing UI is disabled.
- Status: not started

### Phase 3: Perf log parser improvements

- Objective: Make existing release hidden-run logs easier to compare and summarize.
- Expected output: `tools/parse_perf_log.py` support for frame, water, sync rebuild, GPU scope, and particle markers; concise table/CSV/JSON output if practical.
- Dependencies/blockers: Need sample logs from `target/re-flora-logs` or fixtures.
- Status: done for parser structure, GPU/particle markers, latest-log pointer handling, and Markdown/JSON/CSV output; real-run fixture expansion remains a follow-up.

### Phase 4: Water measurement-only diagnostics

- Objective: Add low-risk `--perf` diagnostics that prepare future water optimization without changing simulation behavior.
- Expected output: Metrics for interior fast-path ratio, base-cell particle distribution, G2P/P2G locality hints, snapshot publish cost, command queue pressure, and terrain-cache fallback/skip summaries.
- Dependencies/blockers: Must keep normal non-`--perf` simulation unchanged and avoid distorting hot paths excessively.
- Status: not started

### Phase 5: Water solver readability refactor

- Objective: Split `mls_mpm.rs` into focused internal modules while preserving algorithms and tests.
- Expected output: Separate areas for transfer, terrain cache/projection, density/EOS, diagnostics, and repair/collision helpers.
- Dependencies/blockers: Should follow after Phase 4 or be kept very mechanical; large file split can create merge conflict risk.
- Status: not started

### Phase 6: Behavior-identical micro cleanups

- Objective: Reduce avoidable per-frame CPU/allocation noise without changing output.
- Expected output: Examples include caching per-species color vectors, avoiding repeated style rebuilds when unchanged, replacing small per-frame temp vectors with fixed buffers, and tighter perf-log formatting gates.
- Dependencies/blockers: Each cleanup needs before/after release hidden-run evidence or a clear no-op rationale.
- Status: not started

### Phase 7: Pure-logic guardrail tests

- Objective: Add fast deterministic tests for infrastructure touched by the refactor.
- Expected output: Tests for CLI parsing, log helpers, water GUI config clamping/sync, frame-rate temporal alpha math, queue/revision behavior, and perf parser fixtures where feasible.
- Dependencies/blockers: Avoid GPU/window/audio tests in normal `cargo test`.
- Status: in progress; perf parser fixture tests added.

## Verification Method

Correctness checks:

```bash
cargo fmt --check
cargo check
cargo test
cargo run --release -- --hidden --auto-exit 0.5
cargo run --release -- --tail-latest-log 200
```

Performance/profiling checks when relevant:

```bash
cargo run --release -- --hidden --auto-exit 4 --perf
cargo run --release -- --hidden --auto-exit 8 --perf --water-particles 10000
cargo run --release -- --hidden --auto-exit 8 --perf --water-particles 25000
cargo run --release -- --hidden --auto-exit 8 --perf --water-particles 50000
cargo run --release -- --hidden --auto-exit 8 --perf --water-particles 100000
```

Log acceptance criteria:

- No `error`, `panic`, `failed`, or Vulkan validation warnings in the latest hidden-run log, except known benign messages explicitly called out.
- Existing perf marker labels remain stable unless a change is intentional and documented.
- Profiling-disabled runs do not emit profiler logs or allocate profiler state.
- `config/gui.toml` remains unchanged unless default/config behavior is intentionally changed.

Manual acceptance criteria:

- Startup, loading, camera, item panel, terrain edit tools, water debug spawn, particles, audio pump, and rendering still behave as before.
- Visual terrain edits still publish synchronously with no cross-chunk partial visual update.
- Screenshots and log helper flags still work.

If verification is not possible:

- Record the missing environment, driver, sample log, or scenario in the Progress Log and leave the phase incomplete.

## Open Questions / Risks

- How much old async visible terrain rebuild code should be kept versus isolated later? Current docs prefer synchronous visible rebuilds, but conservative isolation is safer than deletion.
- Water diagnostics can perturb hot paths if implemented inside tight loops; normal builds must compile out or strongly gate deep measurement.
- Large file splits may create merge conflicts with other agents; phases should be narrow and committed independently.
- Some micro-optimizations may be noise-level; measure in release hidden runs before claiming wins.
- Need representative latest perf logs or fixtures before finalizing parser output formats.

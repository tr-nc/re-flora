01 / Direction

我赞同的核心：不是加一堆系统，而是给照料一个去处

用户提出 现在更像沙盒模拟器，希望变成游戏：玩家经营一个 homegrown 餐厅，主要在平房屋顶种植，为楼下提供食物；供给、售卖、收益和再投入让行动相互连接。

我的建议 把主体验定义为“经营一座能端上餐桌的私人屋顶花园”，而不是先做完整餐厅模拟器。餐厅是花园的回声：楼下亮起暖灯、菜品使用了自己的收获、收益让屋顶多一种可能。经营信息要让人有方向，不应抢走种植本身的乐趣。

这次方向带来的价值

  • 从“我能种什么”变成“我想为餐厅种什么”。
  • 裸屋顶提供明确的前后对比和空间作者感。
  • 有限资源让铺土位置、种植组合产生选择。
  • 楼上劳作、楼下营业形成鲜明且容易传播的主题。

需要守住的张力

  • 任务引导 vs. 自由种植。
  • 自给餐厅 vs. 基础资源耗尽后的软锁。
  • 经营反馈 vs. 倒计时、债务和重复打卡。
  • 可编辑土壤 vs. 不可挖穿的模型建筑。
与现有产品文档的关系必须公开说明。
docs/game_direction.md 目前仍是 canonical：Restorative Garden、Gentle Consequence、Sustainable Garden；强调无离线惩罚，基础种植可自我延续，排除强制限时订单，并把大型商店／设备经济推迟。餐厅供给和货币扩展了原来的 Seed Circulation，若变成强制履约就会与现定位冲突。本方案只是新方向提案，本次没有修改该文档。未来获批时应先确认经营压力，再同步方向文档与下属计划。
02 / Brief & scope

把用户原构想拆清楚，不把讨论当授权

主题用户已提出的内容本方案的处理方式
世界背景平房餐厅；方块形的建筑体量，俯视轮廓不一定规整；食物 homegrown；主舞台在屋顶。保留。楼层、屋顶可用面积、外部环境与餐厅室内是否可玩尚未定。
开局没有任何土，只有裸天台；玩家一开始有资源；可以加土、播种和种树。把“无土”作为明确目标。“零可编辑体素”与“零土壤体素”分开确认，不擅自等同。
工具与背包沿用 Grow Item；Dig 临时重命名 Edit，能加能删；底部栏和交互逻辑先不变；没有对应材料不能继续添加。沿用已有交互骨架；材质选择与空库存提示需后续设计。现有库存逻辑不是从零开始。
开发者模式所有方块无限量，方便调试和造景。建议作为显式模式，而不是伪造巨量库存；与正常资源循环分开，标注作弊状态。
经营循环蔬菜供给任务 → 餐厅售卖 → 钱 → 买幼苗、种子、营养土。属于目标构想；任务强制性与收益规则未定。购买系统明确后做。
大物体餐厅、外围造景、通风管等用传统 modeling 与光栅化，加入 Pixelize 风格化处理。以大模型独立流程讨论，不自动转成体素建筑，也不保证一个后处理就能统一风格。
小物体苹果、花头、蝴蝶沿用现在的链路。保留用户的复用意图；当前链路准确含义见现状调查，不把语音里的“贴图”简化成静态贴图。
远期装置／工具可以买并添加通风管，热风可能带来机制；营养土大袋倾倒动画，之后把土弄匀；vintage 风格除草机。全部保留到后续 Plan 不因出现在方案里而获得实现授权。

原话中的“快手，传统的矿山化”“选人”“图”“Grow。Item”等可能是语音识别词。本方案不把它们默默转成确定技术需求：在讨论层面暂按上下文提出候选理解，完整原文在末尾保留。

本次授权仅限：中文 HTML 方案及必要静态资源、只读调查、参考研究、文档验证、提交与推送本分支。没有游戏实现、发布、main 合并、issue 创建、其他 Worker 管理或可见游戏启动。
03 / Repository reality

可复用很多，但“模型屋顶能种土”不是已证明的能力

调查基线 d58b47fe7d2256b7654f3ff663f67d488aae6257。以下为文档与源代码静态阅读结论；本次没有运行游戏或 GPU 验收。

能力读到的现状对新方向的影响
工具 / 相机Playing 记载 Grow、Dig、Smooth、Trim、Water、Inspector、Till、树与喷灌；有 orbit 编辑与行走／free-look 切换。可优先保留操作；“第三人称／上帝视角”还不能自动解释成必须有可见角色。
背包VoxelBackpack 已有按材料计数、回收、扣除，默认零计数；try_shovel_place 没有库存会停止，按实际添加数量扣库存。已有数量约束。当前按固定材料顺序取第一个有库存项，且注释明确忽略材质选择；“对应类型”需要专门理顺。
第一笔土query_terrain_edit_ray_intersection 走 terrain 查询；查询另有树表面特例，未读到通用餐厅模型屋顶适配。在零土＋模型屋顶上必须有真实可拾取的基底、法线、坐标转换与编辑限制；不能依赖已有土壤命中。
建筑场景白石小屋 是独立场景，建筑用真实体素，屋顶已有土／植物，且存档边界受限。可借鉴尺度、气氛和支撑语义，不直接满足裸屋顶＋传统模型的新目标，不应把已有小屋换名后算完成。
小物体画面ModelPixelFrame 管理蝴蝶／落叶、苹果与花等模型像素，含共享表面缓存、每帧姿态／查找／重照明和发布。可复用，不是只放一张静态贴图；大建筑不应未经验证塞进小物体缓存路径。
碰撞 / 水CollisionWorld 决策 区分精确体素碰撞与水的 filled-solid SDF。渲染事务审查 保留 shadow → 外部 moisture → scene 的所有权。模型看得到 ≠ 人能站、土能贴、水不穿、光被遮。要分别确认拾取、支撑、碰撞、水边界、阴影和 DDGI 遮挡。
收获 / 经营玩家指南 仍把完整照料、收获和 Seed Circulation 作为未完成目标。不能把果实掉落等已有局部行为等同于“库存食材 → 供给 → 售卖到账”完整链路；餐厅经营尚未由本次阅读验证。
架构建议：建筑是稳定的模型对象，土壤是可编辑体素，植物沿用自己的生命周期。三者通过明确的支撑／局部环境接口关联，不让建筑为了被种植而必须变成可挖体素，也不绕过现有地形发布、修订与碰撞边界。
04 / The playable promise

先证明一份收获真的能变成一顿饭

建议体验片段 一次 10–15 分钟的小循环。时长承接现有 First Garden Moment 的目标，不是性能或内容承诺。示例作物暂不指定：从已有可用植物中选择能清楚表达生长与收获的一种，若只能用苹果，就先用饮品／甜点表达供给，不假称已完成蔬菜系统。

建议

经营最小信息，不是模拟所有顾客

第一版只回答三个问题：“餐厅现在想用什么？”“我交了多少？”“这次换回了什么？”初期用一个稳定菜品与固定换算，先不做厨师排班、桌位周转、复杂配方、市场波动和供应链。

闭环试验可以先让供给直接触发销售反馈；若没有真实营业系统，必须标为原型规则，而不是伪装成顾客模拟。

建议

把收益反馈放回世界里

一篮收获送到屋顶门口／传递点，楼下窗里有暖光，菜单上出现这次收获的菜，轻量提示说明产物与收益的关系。

这些是候选演出，不是本次新增要求。无需先做可进入、可点菜、可服务的餐厅室内才能表达主题。

建议的正常模式安全网，仍待用户认可：基础种子可再获得，初始土够完成首个循环；缺货时暂停售卖相应菜品，不负债、不倒闭、不因离线扣分。供给请求可选、无强制期限。若用户希望有明显经营压力，需要重新定义并测试，而不是假定低压力已获确认。

不建议用来“游戏化”的东西：为了让数字上涨而增加重复点击、必须每日完成的订单、没资源只能挖餐厅的开局、以及在无限模式下假装正常经济已经平衡。

05 / Space & rules

裸屋顶，是一个清楚的起点

候选空间安排

一个屋顶，四种读图信息

  • 工作区：平整基底，允许自由铺土与种植，不预画强制种植格。
  • 边界：女儿墙、屋沿、排水口，让可用面积一眼可读。
  • 连接：楼梯／屋顶门或供给点，解释楼上楼下的联系。
  • 特色：通风管、旧工具、餐厅招牌；先作为气氛，机制后置。
候选规则

土可编辑，房子不等于土

  • 第一笔土能落在模型屋顶，而非虚空。
  • Edit 删除优先只影响可编辑层，不挖穿餐厅。
  • 添加越界、无库存、无支撑时给清楚反馈。
  • 土被删后植物如何移动／失效需定义，不能悬空。
  • 树的大小、所需土厚与屋顶关系先用简单可读限制，不急做结构承重模拟。
模式资源与编辑应如何区分
正常模式初始资源有限；指定材料不足不能添加；建议按真实净增体素结算，失败不扣资源。库存明确，缺货有原因；单位是体素数量还是玩家可理解的“份／袋”待定。
开发者无限模式用户提出所有方块无限量；建议可选材质并跳过数量消耗，不覆盖真实库存。显式提示“无限资源”，关闭后回到原库存；不视为经济验收。无限资源不应放开无效支撑和非法区域。

若未来实现 Debug 控件，按 GUI settings 规则 走声明式／saved-field 绑定，按“调整项优先”组织；开发者开关默认关闭、是否保存与存档隔离仍待设计，不能用散落的 App-only 控件或每项单独保存钩子。

后续机制候选 热风管可以使邻近土壤更快变干，形成需要观察的小环境，或只做蒸汽与声音；这不等于模拟真实油烟化学，也不宣称热风普遍有益。先确认视觉可读性和温柔后果，再考虑热量／湿度耦合；装置购买与放置另立阶段。
06 / Art direction

像素化的是视觉语言，不是建筑的存在方式

用户提出 大物体使用传统模型与光栅化，风格化后贴近现有 vibe；苹果、花头、蝴蝶等小物体继续沿用现有链路。我的建议 用同一套轮廓、色阶和像素密度规则连接两者，而不是要求两种对象使用同一技术表示。

暖白旧绿叶绿土棕砖红暖灯

建议场景气质：旧而被照料

浅色灰泥平房、朴素檐口、绿色旧金属管、暖色招牌；地面和器物有使用痕迹，但不是废墟。植物轮廓比装饰噪声更重要，远景只提供街区与生活感。

参考 Rosemary’s 的楼上种植与楼下餐厅联系，而不是复制其真实建筑；真实农场的整齐排布不应自动变成玩法网格。

建议先做一个“像素风样板角落”

用一段屋沿＋管道＋土＋一株植物＋一个苹果，在目标镜头下比较：轮廓是否融洽、材质是否抢戏、相机移动是否爬像素、阴影与暖灯是否统一。

可见效果先评审，再独立测 Release 性能。若未来请求 A/B，需要 Debug 运行时复选框保留原版与实验版，不能只靠截图或 CLI。

大场景候选流程 · 不在本次实施

步骤交付目标避免误区
1. 灰盒与镜头在目标上帝视角验证屋顶面积、厚度、边界、楼下可读性；确认正交或透视。不要先制作完整室内或周边城市。
2. 模型与材质简单清楚的体量、足够宽的轮廓、克制贴图频率；碰撞／支撑代理分离。glTF 三角模型加载能力不等于大场景所需的全部管线已接通。
3. 风格化样板评估目标像素密度、色阶、边缘高光／描边、材质分区；保证 UI 保持清楚。只把屏幕降分辨率不能自动解决稳定性、细线丢失和小物体像素大小不一致。
4. 世界语义拾取、种植支撑、人物／果实碰撞、水阻挡、太阳阴影与 DDGI 遮挡分别验证。Raster Consumer 读取光照，不意味着它自动成为 DDGI Occluder。
5. 移动与合成验收平移、缩放、旋转时比较细节抖动，确认透明／水与描边关系；与原有土和植物同框检查。外部 Godot／Unity 做法仅作参考，不能承诺直接套到本项目 Vulkan／Slang 链路。

复古除草机 用户提出 vintage 风格。“手推滚刀割草机”只是候选理解，不等于已确认机器类型。建议先明确用途：整理自生草、收集草屑，还是替代 Trim？若误伤蔬菜会破坏低压力体验，可优先考虑只影响野草／草坪的可读作用区域。未确认前不做购买、操控、刀具动画或复杂草屑物理。

07 / Gated roadmap

阶段边界：先屋顶，再闭环，最后扩展器物

下面是候选实施顺序，每一步均需后续明确授权。本次只完成阶段 00 的方案交付；不在正文里暗含开工许可。

方向方案 · 本次唯一交付

只读梳理、HTML、真实 reference、开放问题与风险。完成标准：离线打开正文与原创图、导航可用，引用与访问限制清楚；提交并推送文档分支。

01

空间可行性与视觉候选 · 获批后

包含：确认方向文档变更；一个平房灰盒＋裸屋顶；目标镜头；一块土可在屋顶上建立，验证拾取、碰撞和支撑；小范围风格样板。

不包含：完整建筑美术、餐厅顾客、购买、热风模拟、土袋演出。

过关条件：无土开局不会失去编辑目标；土不会穿屋顶；模型与植物同框不明显割裂；用户可以评审候选画面。小幅性能问题记录后独立优化，正确性问题不能豁免。

02

屋顶劳作最小片段 · 获批后

包含：Dig → Edit 的命名与双向操作、对应材料选择、初始资源、零库存反馈、显式无限开发模式；沿用 Grow 和主要底栏；验证播种、照料、地形修改后的植物支撑。

不包含：商店、成套新工具和所有植物的营养模型。与阶段 01 的“第一笔土”验证衔接，不绕开底层正确性。

过关条件：正常模式库存与实际净增／回收一致；无限模式开关不毁坏正常库存；裸天台能稳定变成小花园；退出／返回的存档支持若尚未完成，应明确标为限制。

03

一种收获、一份供给、一次收益 · 获批后

包含：选一种现有植物，定义可收获食材；一个供给点、一项餐厅需求与固定收益；让用户看见自己种的东西被楼下使用。

不包含：多菜谱、厨师 AI、实时顾客模拟、限时订单或完整购买。试验若用固定奖励解锁下一种种植，要标注为候选替代规则，不把它当成已批准商店。

过关条件：陌生玩家能解释“为什么种、给谁、得到了什么”；食材扣除与收益只结算一次；无限调试结果不作为经济平衡证据。

04

资源再投入与轻经营 · 未来 Plan

包含候选：购买幼苗、种子、营养土；明确价格、基础资源循环、需求轮换和库存单位；更清楚的菜品／销售演出。

09 / Decisions to make next

只保留五个会改变方案的关键问题

文档已经按保守候选方向完整产出，不需要先逐项回答。下面的“建议默认”都是 Worker 建议，不是替用户做出的决定。

01 · 供给是温柔邀请，还是经营义务？

餐厅缺货时只少卖某道菜，还是有期限、满意度、亏损？建议默认 无强制倒计时、缺货停卖、不负债、不离线惩罚；它最兼容现有 Restorative Garden。

02 · “所有食物 homegrown”具体覆盖什么？

是所有可售菜品都由玩家种植，还是主要食材来自屋顶？谷物、油、盐、蛋白质和其他材料怎么处理？建议默认 初期只卖少量能由已支持作物解释的餐品，其他烹饪辅料先背景化；不默默新增畜牧或全营养供应链。

03 · “第三人称，就是上帝视角”要不要可见角色？

是沿用 orbit 编辑镜头直接劳作，还是有角色走到土袋／植物旁操作？这会改变导航、交互距离与动画工作量。建议默认 第一片段沿用现有编辑视角，不默认加入角色劳作动画；正交／透视先用灰盒比较。

04 · “没有土”是否也意味着没有任何体素？

建筑表面能否用不可编辑支撑代理，树和排水是否有边界？建议默认 没有初始可种植土层，餐厅本体不能被 Edit 挖掉；支撑／碰撞表示不由视觉模型方式直接决定。

05 · 下一次授权的优先验收是什么？

先看裸屋顶＋铺土＋种植的感觉，还是先证明一份收获能给餐厅供货？建议默认 先阶段 01–02 的空间与劳作候选，再阶段 03 的单品供给；购买、土袋倾倒、平整工具、热风管与除草机继续后置。“除草机”与语音中的技术词在相应阶段开工前再核对。

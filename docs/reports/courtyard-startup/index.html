43 秒启动，花在哪里？

结论不是“叶子多，所以启动慢”。最大热点是一个对地形体素与全部树枝做笛卡尔积检查的 CPU 算法；第二类可回收成本来自逐棵种树时反复发布整片树木数据。

基线：4ce0dbcc · 2026-11-02 本机测量 · 仅调研，正式运行路径未修改

02 / 25.7 秒：一个不该做的笛卡尔积

实际查询规模

  • 读取整棵树木包围盒：59,655,104 个体素，分 48 块回读。
  • 排除空气、可复用木材和根部允许的土后，剩余 1,396,954 个候选。
  • 每个候选遍历 1,074 段圆锥枝干。
  • 该场景最终无相交，无法提前退出：1,500,328,596 次精确 SDF 测试。

候选中 1,248,868 个是岩石，148,086 个是高于根部基准的土；大量候选位于宽树冠包围盒下面，却离真实枝干很远。

使用第一轮暖缓存细分样本。进程 CPU 总占用约一个逻辑核当量；结合代码、精确次数及回放，主要热点可归因于 CPU 几何算法。回读数字是同步调用墙钟时间，不能视为纯 GPU 时间。

for candidate_voxel in occupied_materials_of_whole_tree_AABB:
    for branch_cone in all_1074_cones:
        if exact_signed_distance(branch_cone, candidate_voxel) <= 0:
            reject_planting()

根因：检查的保护规则本身需要保留，但它没有使用空间索引，复杂度是 O(候选地形体素数 × 枝干段数)。树冠更宽、基部更粗以后，这个乘积被显著放大。不是单纯“49 万叶子算得慢”。

不能靠绕过保护解决：跳过岩石、允许覆盖已有材质、仅检查主干或只降低叶量，都没有解决这一机制。正确方向是在同一个权威几何与同一个相交判定上，先做空间剪枝。

03 / 闭环验证：相同查询，只读回放

没有把替代算法接入实际种植。先让原算法完整通过，再把同一批候选点、同一组圆锥、同一 <= 0 相交语义送入项目已有的 RoundConeClearanceIndex。它查最近圆锥后，仍使用原始精确 SDF 作最终判断。

每个种子额外检查了大银杏的 4,296 个枝端、中心与边界探针，包含会相交的点；全扫描与索引判断均无差异。两次回放成本不同，是因为空间分布不同，不是候选数量越多就必然越慢。

证明了什么：约 25.5 秒的距离计算内核有明确的空间剪枝收益，同输入回放只需约 0.69 秒。
没有证明什么：这不是已经完成的优化，也不是正式的完整正确性验收；不包含材料筛选与回读，不能宣称“启动已从 43 秒变成 0.7 秒”。

证实了一次过宽的缓存失效

第 3 轮把银杏重新提取了一遍。只读对比发现：包围盒里改变了 208 个材质体素，距银杏真实木材的最小距离为 151.78 体素，远超表面半径 2 的邻域采样。

本例中新增小树的远处木材改变了大包围盒的输入比较，造成不必要的银杏重建。银杏追加耗时从命中时约 0.12 秒升到约 0.61 秒。

这支持改进“实际几何/邻域依赖”的失效判定，但不能直接把缓存规则改成忽略任意远处变化；还要覆盖邻域、重叠树木与玩家雕刻的正确性。

不能说“全部每次从零重建”

已有的每树网格片段缓存有效，5 轮累计命中 9 次。未命中的是全局发布层：整体 BVH、碰撞表面、重新装配、绑定计划和资源上传。

初始场景没有玩家观察中间状态，适合通过权威树木事务批量提交；不是删掉普通编辑时的保护或另建一套初始化树木。

后 4 轮覆盖约 4.41 秒，但不是“保证全能省掉 4.41 秒”：最终完整场景仍要发布一次。实际收益需批处理实施后实跑。

06 / 看起来重复，但优先级很低

同一棵银杏确实生成了 6 次

根区准备、根部定位、成熟边界验证、空间检查，以及放置编译里的当前/成熟树各生成一次。

6 次合计约 0.13 秒。可以复用确定性树形或只计算需要的边界，但即使全部消除，也不可能解决 43 秒问题。

年龄 1 的当前树和成熟树结果一致；更年轻的树并不等价，不能无条件共用。

叶片这轮不是启动瓶颈

一棵大树生成约 535,755 个叶片候选，去重后发布 494,044 个叶片体素实例。

  • 一次整树生成：约 19～24 ms。
  • 树冠音频描述：大银杏约 168 ms。
  • 叶片渲染位置量化：约 37 ms。
  • 大银杏叶片发布：约 144 ms，其中阴影代理约 63 ms、响应关系约 62 ms。

这些阶段嵌套在前面的编译/叶片发布分类内，不能再加一次。大量叶片对运行帧率的影响，本次未测。

07 / 冷缓存与读档：不要混为一谈

运行条件首帧关键差异
原正式二进制，暖管线缓存，未加临时探针43.030 s最初复现，CPU 用户态 41.20 s，系统态 2.18 s。
临时探针，暖管线缓存，第 1 / 2 次细分实跑42.780 / 42.826 s稳定复现；与原版的差异不足 1%，未显示显著探针扰动。
新二进制导致管线缓存未命中70.005 scompute pipelines 约 26.44 s；这是额外冷编译成本，单独列出，不混入 43 秒排序。
移除探针、重新构建后的正式二进制，暖缓存42.520 s重新通过格式、检查、完整测试与 Release 构建；源码无临时探针。
已有庭院存档，暖管线缓存11.757 s没有重新种植的全空间检查；一次准备 5 棵树的表面，约 1.810 s。

管线缓存按可执行文件与设备/驱动身份隔离。重编译后首次运行可能更慢；这里的“暖缓存”是同一二进制管线缓存命中，不意味着庭院地形或树木已经缓存好。每次新庭院仍执行完整生成。

读档不是“只换掉一个算法”的严格 A/B：它也跳过新庭院生成、恢复已存的木材并走批量恢复事务。它印证路径差异，不能直接把两者相减当作某个单项优化收益。

08 / 建议顺序：先修机制，不砍视觉

1

空间查询加速。由种植准入检查复用精确圆锥空间索引，保留原材质保护、世界边界和相交语义。收益证据最强，首先覆盖阻挡、边界、根部、已编辑地形和生长更新，再跑完整 Release 对比。

2

初始树木批量发布。通过现有权威事务所有者，把 5 棵树作为一次初始场景提交，减少整体 BVH、碰撞表面与上传轮数；保留回滚、存档、音频、果实和附着物契约。

3

精细化表面缓存依赖。解决已测到的远处 208 个体素导致整棵银杏失效；把实际采样范围与邻域作为依据，而不是简单“地形版本没变就复用”。

4

专项分析碰撞体导入。当前约 3.6 秒；需要进一步区分几何构建、插入与重复检索，不能只靠减少分帧次数就宣称算法变快。

5

最后清理低成本重复生成。6 次造树总计 0.13 秒、叶片量化几十毫秒，属于低收益项；目前没有理由为了启动速度先砍叶子。

影响与引入：确认影响新庭院生成及同类大树准入检查；已存庭院恢复不走该准入路径。线性全锥检查可追溯至 5b004c54（2026-11-01），成年树形 4ce0dbcc 将规模放大；本次未做历史版本性能二分，不能给出“哪一提交精确增加了多少秒”的结论。
本轮边界：只完成调查与只读实验，尚未实施上述性能修复。临时 Rust 探针已移除，正式源码保持基线；报告及可复现证据单独保留。

测量方法与证据

环境与口径

  • Intel i5-12600KF；NVIDIA RTX 3060 Ti；驱动 580.159.04；Vulkan 实际选择独立显卡，不是 llvmpipe。
  • Release，原生隐藏窗口、静音，物理渲染尺寸 2880×1620；不强制 present mode。
  • 默认新庭院种子 20260519、4×2×4 世界；第二场景种子 7。
  • 嵌套 RAII 墙钟作用域，保留父子 ID 并自动核对时间；CPU/GPU 传输计时不是 GPU timestamp。
  • 15 亿次数按成功准入的候选数量 × 圆锥数推导，避免逐次计数污染热点。
  • 本次没有 perf 采样器；算法归因来自真实接口计时、规模、源码与等价输入回放。没有测量稳态帧率或其它硬件。

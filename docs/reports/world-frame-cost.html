03 / 为什么两项草开销最先变贵

已经剔除，但粒度太粗

草的 FloraFramePlan 先按区块包围盒做视锥与距离判断。区块一旦通过，就把该区块中某物种的全部实例计入光照缓存和绘制；没有继续按实例筛选。

本视角实际提交的草：130,186 → 309,180，约 ×2.37。光照/姿态 band 条目：806,628 → 1,917,184。缓存 compute 按“物种 band 数 × 批次实例数”调度，每个 band 执行姿态与光照采样。

证据：src/tracer/flora_frame_plan.rs:92-151
src/tracer/mod.rs:4931-4997
shader/slang/flora_lighting_cache.comp.slang:47-120

短草仍提交了 8 段索引

物种定义中长草 8 段、短草 4 段；绘制却统一提交 MAX_GRASS_BANDS × 36 个索引。短草的后 4 段直到 vertex shader 才提前返回。

这个视角约有 139,064 株短草。按真实 band 数提交，理论上可从 89,043,840 降到 69,018,624 个索引引用，减少约 22.5%。

这是确定的提交量冗余，不是已测得的 22.5% 帧率提升。当前 LOD0/LOD1 草路径也共用几何索引数，远处草并不会因此自动减面。

证据：src/tracer/mod.rs:5552-5586
shader/slang/grass_band_cached.vert.slang:26-43
src/flora/species.rs:157-183

04 / 另一条时间线：每 0.25 秒的吸水模拟长帧

已确认相关时序，不再只是怀疑。32 区块的读回诊断组中，全部 61 个超过 25 ms 的帧都发生在植物含水更新帧；另一次仅开含水日志的诊断中也是 77 / 77。这解释了周期性停顿，但不能把 CPU 的全部残差都归给它。

实际 CPU 帧墙钟：橙点是含水更新帧

模拟按固定 0.25 秒批次遍历植物根部。涉及植物从 130,366 → 543,501；一次更新的 atlas 读取从 4 → 16 次，每次单独提交并等待。

传输与 GPU 完成等待 · 每次更新平均15.80 ms第一笔约 7.98 ms；后 15 笔合计约 7.82 ms。
读回后的 host 数据复制0.80 ms每轮读取约 8.69 MiB，不是只取根部几个字节。
其余含水函数时间4.88 ms遍历、状态复制、收支计算、上传等，尚未进一步拆分。

每次更新合计：平均 21.49 ms，中位数 26.23 ms，P95 29.80 ms。摊到该组所有帧约 1.72 ms / 帧，但这个平均值会掩盖尖峰。

这些是 CPU 墙钟时间，包含等待之前的 GPU 工作，不能再与 GPU pass 耗时直接相加。传输等待也不等于纯 PCIe 复制耗时。该场景吸水量为 0，当前走干土路径；湿土的写回与水量守恒还必须单独验证。

证据：src/builder/surface/hydration.rs:19-149 · src/builder/plain/mod.rs:576-613

07 / 建议执行顺序：一项改动，一次 Release 验证

草绘制：先去掉确定无用的短草索引低画面风险

从最高的 4.42 ms 操作开始，用批次真实 band 数限制绘制索引数；共享 band 拓扑的前缀已经满足这一点。继续保留动态高度 / 裁剪判断。

验收：长短草、两种 LOD 分组、未长满/被修剪、风动和阴影/深度一致；固定镜头与移动镜头 Release 对比。22.5% 是本视角的索引量空间，实际毫秒收益待测。

草工作集：让缓存与绘制共用更细的可见实例计划中等实现风险

同时针对 4.42 ms 绘制和 3.47 ms 缓存。先衡量区块内无效实例比例，再选择子区块批次或 GPU 实例压缩；不要只裁绘制、仍给所有实例算光照。

所有权：FloraFramePlan / 可见实例映射。保留原始物种、植株索引与种子身份，保守包含生长和风摆边界。不能把本已开启的 pose reuse 再包装成新优化。

含水更新：合并 atlas 读取，减少 4 Hz 停顿顺滑度优先项

现成的 PlainBuilder::read_chunk_atlas_regions 支持一次提交/等待读取多区域；含水模拟目前逐区块调用单区域包装。先批量读取同一时刻的权威快照，再统一结算。

这不是关闭模拟或降低 tick。若进一步异步化，必须保证地形编辑、删除植株、土壤水分和分数余额的版本一致；不能用过期读回重复扣水。湿土写回也要覆盖。后 15 笔等待的 7.82 ms 是当前成本，不是承诺可全部省掉的收益。

花茎预计算 / 花模型绘制：合并细碎批次次级热点

准备约 1.73 ms、绘制约 1.37 ms。准备路径按“区块 × 物种”多次调用；优先检查小 dispatch、资源依赖和同类批次聚合，而不是先降花模型质量。

验收：根部固定、花头连接、风响应、逐株颜色与深度。给单次准备和绘制加更细计数后再判断具体瓶颈，不把整个 prepare 时间都认定为着色器算术。

再看 DDGI / 阴影 / UI，以及剩余 CPU 残差后续按实测重排

当前单项约 0.2–0.65 ms，优先级低于草和同步停顿。DDGI 总探针增加 4,913 → 18,513，但每帧 32,768 条射线预算未变。远处草减面、跨帧缓存和降探针质量都可能改变画面，需独立视觉对比，不作为无风险修复。

前面每完成一步都重新排序；若 CPU 残差成为主导，先补定向计时再动实现。不能把“没有细分”当作“没有问题”。

执行原则：保留 4×2×4 世界，不通过缩世界、隐藏植物或关阴影来宣布成功。每项只用真实 Release 帧数据验收；检查平均、尾部和原始场景，不把父子计时相加，也不把 GPU 节省直接换算成 FPS 承诺。

08 / 引入时间、边界与可复查证据

回归触发于 8d98fc5a（2026-10-30 23:08:44 +0800）的世界扩容。草的整批处理、固定 8 段提交、含水同步逐区块读回在扩容前已存在；扩容放大了这些路径的成本。本轮没有改变生产代码、配置或画质，没有提交未经测量的“优化”。

计时完整性

普通 profiler 容量 64，32 区块稳定帧会溢出 2 项；总帧 scope 与前部草 scope 仍在。完整 GPU 榜使用 RE_FLORA_STEM_PIXEL_PROFILE=1 的 1024 容量，dropped=0。

当前源码中此开关只选择查询容量，并未切换草算法。总帧比较仍保留独立普通采样组，避免把诊断模式差异混为优化收益。

显存遥测全程峰值约 4,191 MiB（含桌面），低于 8 GiB；没有观察到内存耗尽错误。此数据不能推广到低显存机器。

尚未覆盖

  • 不同用户存档、相机运动、连续编辑与更多视角。
  • 湿土吸水、浇水期间写回，以及其他 GPU / 驱动。
  • 任何候选优化的实际加速比与图像等价性。
  • CPU 未分类残差及单个 shader 的内部指令成本。

因此本报告是本机归因与优化队列，不是全平台性能验收。

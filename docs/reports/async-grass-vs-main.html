01 / A fair comparison

先划清收益归属

这是一份当前分支的增量评估，不是把此前所有优化汇总成一份“加速清单”。

这次真正改变的路径

无限材料模式下，交互式 Grass Mix 笔刷

当前构建的无限材料开关为 true，所以普通玩家试用这个构建时会走到新路径。请求最多覆盖 8 个区块；超出范围仍走同步路径。

  • 输入接收请求，稍后提交私有 GPU 编辑。
  • 正常逐帧轮询完成情况，而不是每次立即等待。
  • 所有区块准备完成且版本仍有效，才一次性发布。
不要计入本分支收益

1 FPS 修复、普通静态 FPS、地形编辑加速

草地音频显存读回修复 1efbd1be 已在两边，不能算作 Async 的优势。这个分支也没有把整个渲染器、挖土或付费种植变成异步。

  • 有限库存种植、花卉种植保持同步。
  • 拔草、修剪、挖土、放土保持同步。
  • 脚本 API 的“返回即完成”约定没有改。

03 / What is actually gained

收益在调度与一致性，而非更少的 GPU 工作

main / 同步
准备 + 提交
→
主线程等待 GPU 完成
→
读回 + 更新
Async / 分阶段
私有副本 + 提交
→
旧场景可继续使用
按帧轮询完成
→
校验 + 整体发布

流程示意，不按耗时比例绘制。GPU 编辑与渲染仍使用同一个有序 general queue；CPU 不立即等待，不代表渲染提交不会排在编辑之后。

已实现、已验证的价值

  • 旧状态可用，发布原子化。多区块输出未全部准备好时，不让部分新结果提前进入 live 场景。
  • 独立输入和输出。私有副本避免用“版本号检查”冒充真正的 GPU 读写隔离。
  • 有界冲突恢复。实例、竞争生长字段或地形版本变化会拒绝旧结果；两次重试后同步完成，避免无限重试。
  • 保留当前含水量与保存顺序。发布读取最新水分状态；保存前排空已接收编辑。绘制与音频读回共同发布。
  • 容量防护。shader 越界写保护配合事务容量检查，防止私有输出越界后被发布。

有潜力，但尚未证实的玩家收益

在“同步等待很长、私有副本准备很便宜”的设备与场景上，分阶段完成可能给主线程留出更多时间处理其它工作。这是合理的设计动机，不是本轮测量结论。

“发布”只代表场景状态变为可用，不代表像素已经呈现在显示器上。连续拖动时的整帧 P95 / P99、光标响应和输入到显示延迟，本轮没有测量。

04 / The price of isolation

成本没有消失，只是换了位置

01 / MAIN THREAD

准备工作仍在主线程

私有资源分配、实例快照、竞争生长字段上传都在提交阶段进行。当前热点是提交准备，不是最后的发布。异步没有把这部分自动移到后台线程。

02 / MEMORY

空间换隔离

第一次使用创建一对 256³ R32UI 工作图像，合计 128 MiB，之后复用。每个事务另建最多 8 个区块的实例、生长、含水量与读回资源；旧帧资源还需延迟退休。未测实际峰值占用。

03 / BOUNDARIES

并非处处无等待

只有一个已接收请求槽。新笔刷、同步编辑或保存可能先排空前一个请求；高冲突会回退同步。退出会取消尚未发布的无限材料笔刷，而保存会等它完成。

维护成本：新增请求状态机、私有资源生命周期、缓冲写版本、整体发布与帧退休约定。共享 GPU 编辑实现避免了算法复制，这是正确的结构；但这套结构需要持续做跨路径一致性验证，不能只看一次性能数字。

历史记录支持“这个策略在某些环境能减少主线程端耗时”。它同样没有宣称已证明输入到显示更快。

为什么不能直接复用那些百分比？

现在比较的是合入音频读回修复后的两个版本。当前 main 的同步路径也受益于适合 CPU 的草实例读回；与此同时，本机是离散显卡与 MAILBOX，而不是 Apple 统一内存平台与 FIFO。

这些差异都有可能改变等待 / 拷贝的成本比例。现有证据不能把反转单独归因于某一项；要分别量化原因，需要同提交跨设备测试或进一步分段 profiling。

06 / Recommendation

把它当作可验证的基础，而非已兑现的加速

我的建议：保留实验分支，暂缓以性能优化名义并回 main。

如果目标是“当前这台机器刷草更顺畅”，现在还没有足够理由选择它。若目标是建立可靠的延迟发布能力，这个分支已经完成了有价值的一步，而且合并后的正确性检查覆盖了关键边界。下一步应围绕测到的成本做针对性验证，而不是扩大异步范围。

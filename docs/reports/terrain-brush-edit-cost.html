01 · 等待提前了，账并没有少

密草单 chunk 添加 · 中位数

正常调用9.51 ms
先 wait_idle，再计调用3.28 ms
把提前等待加回每笔总账9.92 ms

第三项是逐笔 preflight + edit 后再取中位数，不是两个中位数相加。各模式 60 笔；环境有漂移，不能把差额当严格同帧 A/B。

证据链已经闭合

正常渲染与编辑使用同一个 general queue。编辑提交自己的任务后立刻等待完成，因此它必须等此前任务及依赖。

提前排空后，密草挖地 job wait 从约 6.33 ms 降到 0.216 ms，但 preflight 自己变成约 6.67 ms。修改 kernel 仍只有几十微秒。

这定位到自身 kernel 之外的队列 / 完成等待；没有系统级 trace，不能进一步把每一微秒都归给 vsync 或某个 draw call。

被否定的捷径：提前 wait_idle 只是搬移耗时，不能作为优化。IMMEDIATE 呈现模式也没有稳定收益，不改你的默认呈现设置。

03 · 草刷真正的固定工作，也没有消失

局部一笔仍然走整块流程

表面重建 → 清占用图 → 实例转占用 → 笔刷编辑 → 重建实例 → CPU 含水量对齐。

三个 pass 覆盖整个 256³ chunk。半径从 14 缩到 2，capsule edit 仍约 .155 ms。已满区域重复刷，也照付整笔开销。

这里指无限材料模式的普通草 capsule；有限种子种草已经是单根追加，模型花卉也有不同路径。

04 · 优化顺序已经明确

01

先改编辑事务的同步完成边界

让录制、提交、异步完成与发布归同一个 owner 管理，避免主线程中途多次等共享队列。明确 in-flight atlas 读写、scratch 生命周期、库存结算和可见 revision；不是简单删除 wait，也不是换个线程就结束。

02

地形没变，草刷不应反复重建整块表面

复用带 chunk / terrain revision 的可种植表面或活跃砖，或从局部 atlas 提取。现有 surface 是共享临时资源，不能直接删调用，也不应盲目给每块缓存一张 64 MiB 全图。

03

再把实例、存活与含水量改为增量维护

移除 / 修剪 / 存活检查按现有根处理，添加按局部表面处理；保持根身份与状态，减少全图往返和整块 CPU 重排。保留幂等、草类型排他、出生时间与埋藏规则。

不改连线兜底，不先增加补点。

80 ms 采样间隔仍是独立上限。降低单笔成本可以减少主线程额外停顿，但不会自动恢复未采到的轨迹；真实输入到显示的延迟需在实现阶段另测。

局部一笔，成本在哪里放大？

普通草 capsule 绘制 无限材料模式

  1. 按笔刷包围盒选 chunk长线、跨边界会扩大候选范围。
  2. 重新构建该 chunk 的表面已有 sparse surface 优化，但仍需执行并等待。
  3. 清占用图 → 实例写入 → 编辑 → 重建实例clear / edit / rebuild 三次完整 256³ dispatch。
  4. 读回所有普通草实例，重新对齐状态CPU 根集合、含水量映射及上传随整块草数量增长。

这是优先缩小工作量的对象，而不是继续优化 capsule 的几次距离运算。

地形挖 / 填 保留草状态

  1. 笔刷 AABB 内修改体素atlas 修改已局部化；统计和粒子采样一起执行。
  2. 提交 general queue，主线程等待CPU 计时混合了排队、实际执行与同步。
  3. surface → contree → scene texture按候选 chunk 重建；保留草路径仍有串行等待。
  4. 草存活检查与派生系统通知有草 chunk 的存活检查仍走整块 occupancy。

应分别测「改体素」和「发布这一笔」，不能只盯着写入 shader。

适用范围：有限种子种草已经走单根追加，不走上述完整草刷流程；模型花卉是另一条 authored 路径。它们不能混用基准。

草：极小编辑也有固定扫描成本

验收 fixture 中，两次微小草移除的 occupancy GPU 子流程为 0.738 / 0.767 ms；两次存活检查为 0.793 / 0.824 ms。

不含表面重建与 CPU hydration，对普通草添加也不是完整笔刷基准。证据支持「固定成本存在」，不支持承诺完整提速幅度。

土壤变绿：已有增量路径

1,024 / 65,536 个根的 fixture，单根变化后的 soil-cover refresh 中位数分别为 0.198 / 0.246 ms。

每档 12 次，仅计 refresh，不含前置实例/含水量对齐。无变化约 0–0.001 ms，暂时不优先重写。

不能把读回与等待混为一谈。统计、采样结果的 CPU 复制各约 1 μs 或更低；约 7 ms 在此前的任务提交与等待。下一步需要独立 GPU timestamps 和 queue / wait 归因。

建议怎么做，而不是先做什么小技巧

补齐一笔的分段基线

草 add/remove、地形 dig/place，覆盖稀草/密草、长段/短点、跨 chunk。分开 GPU 执行、等待、CPU 状态对齐和后续帧；先定位 7 ms 的真正来源。

让草编辑按局部表面 / 现有根工作

移除、修剪、存活检查遍历根；添加遍历局部可种植表面并查重。稳定根身份，增量维护含水量与结构变化，避免每笔整块重排。只缩小 edit dispatch 还不能消除另外两个全量 pass。

让地形派生重建跟着真实变化走

跳过无地形变化的重建，但保留植物清理语义；再收紧 dirty bounds / chunks。砖级更新必须维护法线邻域、跨界草存活及碰撞/光照依赖，不能靠降低质量换速度。

等待确实主导时，再做提交流水化

独立 scratch、批量提交和延迟读回需要明确的所有权。不能直接删除 wait 或把旧逻辑丢到后台线程：库存、可见 revision、拾取和 GPU 资源生命周期都要一致。

这次不动连线兜底，也不先提高编辑频率。

80 ms 节流与单 pending pick 是独立上限。降低成本能减少额外停顿；若以后要保留更细轨迹，再单独讨论高频输入采样与编辑消费解耦。

证据能说明什么，尚不能说明什么

已确认：整块工作放大、串行等待、固定采样间隔；Release 小范围挖地及稀疏草 GPU 子流程的实际成本。

尚未测：完整普通草添加、密草 CPU hydration、长 capsule、真实鼠标到显示的 p95。尚无候选实现，因此没有提速百分比或性能验收承诺。

Release 构建与 hidden/mute smoke 成功。5 个研究运行均成功退出，日志未见 ERROR / VUID / panic；源码、生成文件和 tracked 配置未改。历史 RTX 数据没有作为本机证据。

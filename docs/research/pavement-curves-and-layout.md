# 铺路弯道：现实铺装、Tiny Glade 与当前几何限制

调研日期：2026-10-12。代码基线：`4ea6b36b`。

## 问题与证据边界

玩家在 `--flat-terrain` 的纯平地形上仍然遇到转弯拒绝：横向三块石板中，内侧那块看起来远未压缩到三角形，系统却不再允许继续铺设。

本次只调研与诊断，不修改铺路算法。证据分为：

- **源码事实**：当前代码确实先检查固定圆角的可容纳性，之后才生成石板。
- **独立几何实验**：调用现有 `PavementRecipe::pieces`、`inset_quad` 和 `PavementCoverage`，证明部分被现有规划器拒绝的曲线可以产生合法四边形石板。
- **玩家观察**：平地上复现，说明地形起伏不是出现这个问题的必要条件。但没有采集这次拖动的世界坐标，不能声称已精确重放同一次手势。
- **外部一手资料**：铺装厂商施工手册、施工专家本人撰写的实例，以及 Tiny Glade 官方公告和开发者原话。

几何实验不是 GPU 体素化、地面支撑、真实逐帧发布或全交互端到端验收。公开描述也不等于获得了 Tiny Glade 的内部实现。

## 结论

**当前限制回答的是“指定半径的圆角能否塞进当前折线”，不是“石板还能否继续合法变形”。这两个问题不能等同。**

需要保留不折叠、不覆盖已有物体、可靠落地等硬约束；不应把某一种排布策略失败直接提升成整条路线不可铺设。最小改进方向是先充分利用现有四边形的变形余量，而不是立即引入大型通用求解器，也不是直接降低一个半径常数便宣布修复。

## 1. 现实铺装如何转弯

### 1.1 普通砖铺面：维持花纹，再沿边界切割

[Pavers by Ideal 的施工手册][ideal]（印刷页码 8）要求，曲线路面先把选定花纹铺到边界以外，再标记、切掉边缘；原文明确写道：

> Do not attempt to turn the pavers to follow the curves.

这是普通铺面花纹的做法，不是对所有扇形铺法的否定；同一手册也另外讨论了圆形和扇形花纹。

**启示**：曲线道路不必等同于“每一排砖都垂直于中心线”。保留铺面花纹、裁剪到道路边界也是合法的生成策略，但改变视觉风格，应与当前随路径转向的排布分开考虑。

### 1.2 随曲线转向：把石材加工成楔形／梯形

施工专家 Pavingexpert 的 [Curve detail / Taper Cutting][detailing] 展示了单侧和双侧切楔形的做法：较紧的弯需要加工石块，以控制接缝并维持平顺的边缘。

其 [Fan Radius][fan] 专门展示随弯转向的石板铺法。共同朝向圆心的接缝形成扇形，相邻石板通过切割适配，而不是维持所有矩形尺寸不变。

现实中的砖石不被物理压缩；游戏中的网格变形，可以在视觉上表达“为这个位置加工了一块合适的石材”。不能把这种风格化几何解释为真实材料弹性。

### 1.3 内侧过小：改变分块，不是宣布整条路不能施工

[Fan Radius][fan] 展示了在内侧用一块较大的“double piece”替代两块过窄石板，以及用 cap stone 替代尖碎块的实例。[Cutting-in][cutting] 也介绍用半块、整块或不同方向的石块打破局部花纹，避免难以保留的细碎边角（inboard cutting）。

**启示**：可以保持道路意图，但放松“每排都恰好有同样数量的砖”这一实现假设。内侧合块、改变纵向排距、局部切块，都是不同层次的适配手段。

现实资料并不支持“所有石块都必须压到零边长才允许换排法”。细长尖片存在强度和施工问题；游戏也存在接缝、最小可见面积和体素分辨率问题。不过这些限制应来自实际形状与表示能力，而不是任意固定的整条路转弯半径。不要直接把现实工程的尺寸建议换算成我们的游戏阈值。

## 2. Tiny Glade：能确认什么，不能确认什么

### 已确认的公开行为与开发原则

- [官方商店介绍][store] 描述了砖、石子和木板按玩家操作适配；路径穿过建筑会生成门，抬高建筑会生成支撑。
- [2023-04-27 官方开发日志][diary] 说明路径与墙形成拱、路径遇到陡坡会形成台阶；还记录了为适应地形高差而重写拱生成器。开发者称其为多条定制程序化算法相互衔接，而不是一个“神奇算法”。
- [2024-05-30 开发者采访][interview] 中 Anastasia Opara 明确说明：先考虑期望的体验，再设计支持它的管线；不同元素拥有针对性的生成器，支持 creation、assembly、morphing、deforming。

官方日志的可读正文提取不完整，已在官方页面原始 HTML 的内嵌公告正文中核对上述段落，不以转载摘要代替原始证据。

### 本次未找到的细节

在本次核对的官方页面、公告及采访中，没有找到足以复刻其曲线铺路的具体算法、砖块拓扑转换规则或曲率／压缩阈值。因此不能声称它使用某个确定的优化器，也不能把我们建议的“内侧合块”说成 Tiny Glade 已公开的做法。

**可借鉴的是行为合同**：优先实现玩家想画的形状，再让局部构造适配；不要把内部模板是否容得下，直接变成用户输入是否允许。以上是基于开发者描述提出的设计借鉴，不是对其内部代码的反向工程结论。

## 3. 我们现在的限制到底从哪里来

| 层次 | 当前规则 | 代码位置 |
| --- | --- | --- |
| 圆角规划 | 每次以整条道路宽度 `W` 作为圆角半径 `R` | `src/app/path_band.rs:200,273,317` |
| 折线转角 | 单个控制点的方向变化超过 120°，标记不连续；不是整个弯累计转过 120°就拒绝 | `src/app/path_band/curve.rs:13,139` |
| 圆角占用 | 每个角沿相邻线段占用 `R * tan(angle / 2)`；同一线段两端占用和超过长度的 98%，标记不连续。末端只有误差极小的特殊弧段处理 | `src/app/path_band/curve.rs:142-181` |
| 冻结截面续接 | 重建尾部时，第一排出入口夹角限制为 `pitch / W + 1e-4` | `src/app/path_band.rs:436-444` |
| 候选交互 | 扫描整个待铺尾部，发现一排 `!valid` 就拒绝当前端点 | `src/app/core/pavement.rs:105-141` |
| 石板生成 | 无效排直接不生成石板；有效排划分固定横向条带，按真实距离向内收出接缝 | `src/app/pavement.rs:55-101` |
| 四边形安全 | 原始和收缝后的四边形都必须严格凸、有限、不反转 | `src/app/path_band.rs:85-113` |

**前四层没有计算“内侧某块砖压缩到几成了”。** 实际石板四边形是在它们之后才构建的。

固定 `R=W` 的意图是防止内侧折叠并给流式发布留稳定余量，但它不是“几何必需的最小半径”的推导。用这个约定生成圆角失败，不能证明其他合法形状不存在。

代码已有石板网格变形：`ground_piece` 通过 `PathCell::point(u,v)` 将生成石材映射到四边形（`src/app/core/pavement.rs:566-618`）。当前并不是“只有刚性矩形”，而是尚未充分利用现有变形能力。

另外，非法预览会被改成直矩形后画红色（`src/app/core/pavement.rs:161-183`）。其挤压／交叠形状不是一个真实变形方案的求解结果，不能拿它来衡量内侧剩余的变形空间。

## 4. 为什么“还没到三角形”这个观察成立

只考虑平面圆弧、等宽道路和法向截面，暂不计接缝。设中心线半径为 `R`，道路总宽度为 `W`：

```text
内侧半径 = R - W/2
外侧半径 = R + W/2
内侧弧长 / 中心弧长 = 1 - W/(2R)
```

因此，当 `R=W` 时，内侧弧长仍为中心弧长的 **一半**。还不是零边长，也没有退化成三角形。

对于两个截面之间的四边形，若中心线排距为 `p`，圆心角为 `p/R`，其内侧直边长度为：

```text
L_inner = 2 * (R - W/2) * sin(p / (2R))
```

在这个特定模型中，`R=W/2` 才会把最内侧两角压到同一点。`R>W/2` 是该圆弧条带不在内侧退化的必要条件，但**不是实际石板足够厚、接缝能保留、全路径无自交的充分条件**，不能直接作为新算法唯一的合法判据。

### 使用现有石板生成器的单排实验

参数：Slabs、`W=0.12`、`p=0.05`、seed 42，横向三块；截面取自精确圆弧。现有物理接缝约为 `2.5/256`。压缩率是相对中心排距 `p` 的原始内侧直边缩短比例，不是砖体积变化。

| R | 收缝前内侧边长 | 缩短比例 | 现有生成器得到石板数 | 收缝后最短边（体素） |
| --- | ---: | ---: | ---: | ---: |
| 0.180 | 0.033226 | 33.5% | 3 | 6.331 |
| 0.120 | 0.024819 | 50.4% | 3 | 4.327 |
| 0.100 | 0.019792 | 60.4% | 3 | 3.125 |
| 0.090 | 0.016453 | 67.1% | 3 | 2.325 |
| 0.080 | 0.012298 | 75.4% | 3 | 1.329 |
| 0.070 | 0.006992 | 86.0% | 3 | 0.054 |
| 0.065 | 0.003752 | 92.5% | 0 | 接缝收缩失败 |
| 0.060 | 0 | 100% | 0 | 原始四边形退化 |

这个表还揭示另一项边界：`R=0.070` 数学上能返回三块，但最短边仅 0.054 个体素，绝不能据此宣称它可可靠落地或显示。三角形也不能简单通过关闭检查得到；当前 `[Vec2;4]` 足印、严格凸收缝和网格非退化检查，都没有专门的三角单元路径。

### 完整弧线与候选输入对照

- `W=0.12`、`p=0.05`、`R=0.10` 的四分之一圆，按精确圆弧截面交给现有生成／收缝／间距检查，得到 **12 块石板**，无折叠，现有间距检查通过，最短边约 **3.125 体素**。
- 同样半径的圆弧，180 次等角度输入（每次 0.5°）进入现有路径编译器，最终有 2 排 `!valid`；隔离调用当前候选交互方法，40 次输入被拒绝，最终仍为 `Turn`。
- 只在临时诊断器里降低圆角策略半径，不变道路宽度和石板生成，同一例子的上述几何／候选拒绝消失。这是区分原因的单变量探针，**不是已经验证的修复方案**。
- 另一个有足够空间的 90°折线，最终编译有效；逐步画出其短末段时，中间有 10 次候选被拒绝，移远后恢复。短尾部暂未排好与最终无法铺设被混为一谈。

临时探针位于 `/tmp/re-flora-pavement-diagnosis.rs` 与 `/tmp/re-flora-diagnosis/`，不是仓库的永久回归测试。它省略世界支撑、GPU预检和发布；以上数字不能替代真实逐帧输入测试。

## 5. 推荐的改进顺序（待批准实施）

### 第一阶段：把硬约束从规划偏好里分离出来

1. 将道路宽度与圆角策略半径解耦；先求可适配的未落地曲线／截面，再根据实际石板足印验证，而不是以 `R=W` 当作普遍几何必要条件。
2. 充分使用当前梯形／四边形石板，不必为了本次问题先引入全局铺装优化器。
3. 允许未落地尾部继续调整；区分“还在排布的暂态”和“确定拒绝”。不得把地面缺失、真实重叠等硬失败伪装成暂态。
4. 保留已经发布的体素与出口截面，不能靠抹除旧路来伪装流畅；变形、预览、支撑、间距和体素写入必须消费同一份最终几何事实。
5. 最小可用边长、面积、接缝和体素化余量要从实际表示能力验证得出；不要用一个新的神秘比例替换旧的神秘比例。

### 第二阶段：只有确实需要时才改变局部分块

当四边形的合法变形空间真的不足时，再考虑内侧跨排合块／少块、局部排距变化、切块、专门的三角或扇形转角单元。它们是排布拓扑变化，不是放宽凸性检查。

先决定要保持怎样的视觉花纹。现实里的“保持全局花纹、边界裁切”也是候选，但与当前“横排跟随道路”的样式不同，不宜悄悄替换。

### 验证应围绕玩家行为

- 平地、三块宽道路上的缓弯；同一曲线使用不同鼠标事件密度。
- 从直线逐步转弯，短末段不能在仍可适配时锁死输入；恢复后不跳过路段。
- 原有固定半径边界两侧的曲线，不能一律以旧边界判失败。
- 左右弯、S 弯、保存宽度／长度极值，以及已经铺出前缀后的续接。
- 真正回折、交叉、已有铺装和无支撑地面仍然安全拒绝。
- 若采用局部合块／三角单元，验证它们的接缝、封闭网格和真实体素覆盖，不能只看轮廓。

## Repro loop

Opt-in `RE_FLORA_SOIL_PERF_REPORT` adds a release app replay, not a normal unit test. A seeded supported fixture is generated by the existing deposition planner, uploaded once, published and warmed up. Each measured event adds the saved batch through `App::apply_soil_deposition`, including real atlas transfer, Visible Terrain Publication and normal native Vulkan rendering. Final count and atlas hash lock down workload/correctness. It does not reduce the request volume or change the user's settings.

```bash
env -u WAYLAND_DISPLAY \
  RE_FLORA_SOIL_PERF_REPORT=target/soil-perf/baseline-large-1.json \
  RE_FLORA_SOIL_PERF_MAX_P95_MS=33.333 \
  RUST_LOG='warn,re_flora::app::core::soil_performance_bench=info,re_flora::builder::plain=info,re_flora::run_log_binding=info' \
  flock --close --timeout 120 /tmp/re-flora-summer-gpu.lock \
  cargo run --release -- --hidden --mute --rooftop-poc --perf --auto-exit 60
```

The optional33.333ms gate is a repro of the reported approximately30FPS hitch scale, **not** a new project acceptance budget. The first run failed it: frame p9587.109ms. The report is written before the failure. Omit the gate for regular measurements.

This is **fixed work**: one batch every three rendered frames,240 measured frames and80 events after60 warm-up frames. It is equivalent to the default20Hz at a60Hz logical schedule, but it is not wall-clock holding and its equivalent FPS must not be presented as the player's sustained FPS. A wall-clock held-input follow-up is needed for acceptance.

## Ranked hypotheses before targeted probes

1. **Adaptive readback/replay**: if repeated small sampling and replay dominate, retaining a safely invalidated sampling-reach hint will remove repeated expansion without changing atlas bytes.
2. **Per-grain CPU settling**: if neighbor/column lookups and radial distance work dominate, a behavior-equivalent planner data path will lower planning time while preserving seeded byte-identical output.
3. **Visible publication**: if chunk rebuild/invalidation dominates, deposition planning alone will not deliver a proportional frame gain. Keep coherent synchronous publication; do not hide work with delayed inconsistent terrain.
4. **Rendering large geometry**: if the static geometry is the primary cause, large idle frames should be similarly slow. Initial idle control argues against this as the main edit-spike cause, but GPU scopes remain relevant.

No10×/100× total-speedup claim is justified by these initial measurements. Stage profiling and repeated order-reversed matched runs come next.

## Stage probe and variability

The next matched large-pile run preserved hash`299ee6dcf37284dd` but was faster than the first run: event mean27.371ms, median26.607ms, p9531.017ms; frame p9533.382ms. **The original86ms event tail is not a stable baseline.** Use repeated interleaved measurements, not the most dramatic first number.

Stage means across80 events: readback9.564ms, planning9.912ms, crop0.146ms, upload1.454ms, dirty flags0.108ms. Visible publication contributes the remainder, roughly4–8ms depending on affected chunks. Each event reads8125440 bytes including one speculative replay. `perf` is not installed on this host; no CPU flame graph is claimed.

Primary-source research:

- [NVIDIA APOD and strong scaling](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#strong-scaling-and-amdahl-s-law): assess hotspots and bound fixed-work total speedup by the fraction actually optimized. Its memory guidance prioritizes minimizing host/device transfers. These are general principles; this application is Vulkan/Rust, not CUDA.
- [Khronos CPU/GPU synchronization sample](https://github.khronos.org/Vulkan-Site/samples/latest/samples/performance/wait_idle/README.html): broad idle waits drain the GPU pipeline; per-resource fences can avoid some bubbles. Its22% Mali example is **not** a prediction for this GPU/application, and visible terrain still must publish coherently.

Probe logging is opt-in to the soil benchmark, `[PERF][SOIL_STAGE]`, with read/plan/crop/upload/dirty timings and transfer bytes. Stage report: `target/soil-perf/profile-large.json`; log `/tmp/terrain-magic-soil-perf-profile-large.log`. `cargo check`, Release build, matched replay and ordinary hidden startup passed; source/planner behavior did not change.

## Experiment1: reuse a sampling-reach estimate

A new saved runtime checkbox, **Debug → Soil Deposition → Soil: faster sampling and settling (A/B)**, leaves the original path unchecked and selects experiments checked. Default remainsunchecked for comparison. Benchmark `RE_FLORA_SOIL_PERF_FAST=1` selects the same saved field in memory, not a separate production algorithm.

The candidate remembers only the accepted horizontal sampling reach near the previous stroke and within the same legal bounds. It does **not** cache occupancy: every request still reads authoritative atlas bytes; misses/changed locations use the original minimum, and expansion/replay still handles growth. Changing terrain or material cannot make cached bytes stale because no bytes are cached.

Matched same-binary large run: original event mean26.946ms/median26.347ms/p9530.589ms; reach candidate mean21.126ms/median20.280ms/p9524.470ms. This is approximately1.28× event improvement, not10×. Frame p95 reduced32.668→26.522ms while mean remained17.07→17.04ms. Hash`299ee6dcf37284dd` and40960 added voxels match exactly. Candidate expands once on the first event, then reads6500352 instead of8125440 bytes with no repeated speculative plan. Artifacts: `target/soil-perf/{reach-baseline-large,reach-large}.json`.

Reach guard test, full deposition regressions, generic saved-field round-trip, cargo check/Release build and normal hidden smoke passed. No shader change. The checkbox is source-declarative; generated GUI changes follow from cargo check. User spread13 remains local.

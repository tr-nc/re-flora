结论：值得做，但不是“加一个湿度值”就结束。

推荐先做喷中偏转 → 离开回弹 → 湿后下垂 → 缓慢恢复。动力来自水流，湿重改变静态形状和局部恢复感；不用“越湿越抖”替代力学。

01 / 草

一株一个 wetness

每根草的叶面湿润量统一控制外观和下垂。另存紧凑的偏转、速度，根部固定；不为每层、每个 voxel 重复更新水状态。

02 / 苹果

每颗独立被推开

在实际高度与挂点接收水流推力，绕挂点回摆。挂着时不用完整刚体；喷水不默认触发掉果。

03 / 树叶

局部颤动，轻微下垂

复用现有叶响应；湿度尽量按小叶簇锚点共享。水只推被覆盖的局部，不让整棵树一起摇，不反向求解枝干。

已根据你的最新反馈收敛：草、叶、苹果不截断彼此的水流；terrain 必须阻挡。第一版不做树冠截留、水量重新分配或滴水二次灌溉。

为什么先给报告：实际代码中的草/苹果共享二维响应场，而水有高度；草的历史状态也不能绑定绘制序号。低阶模型很直观，但正确接入需要处理状态归属、帧顺序和地形遮挡，不能只加一个 shader 抖动参数。

先区分两种感觉：冲击，和湿重。

拖动时间轴，或播放同一段受力过程。取消“湿重”只去掉示意中的附加质量与下垂，不去掉水流推力。相向喷洒时，净定向力抵消，湿润仍累积。

不是越重越容易乱抖

水流输入冲量，弹性与重力负责恢复。固定刚度下，增加质量会降低固有频率；恒定推力最终形成偏转平衡，不会无限自发抖动。

依据：真实叶片冲击实验 [1]、阻尼振子 [3]

苹果不照搬湿草的公式

理想小角度单摆的周期不依赖质量。苹果的表现重点是“被推开、再摆回来”，不是因为表面挂水就明显变慢。水滴对叶片阻尼也不是普适常数。

依据：单摆 [3]、液滴与悬臂共振实验 [2]

单 ray 的边界：一条代表水束一根中心线可以；整个扇形喷幅只测中心一根，遇到“半堵墙”就可能漏判。新增反馈优先复用当前 terrain sweep，不另做逐植物多 ray，也不为省事删掉原有墙边裁剪。

不新增树冠遮挡

前面的叶子不会削弱后面的水，也不产生截留水量。苹果与草都只是被动接收者。这与现有 terrain-only 喷流一致。

不从“雾有多浓”推算力

当前空气密度场是光学用途，关闭雾或改雾强度会影响它。植物输入应来自共享水源；关雾、关粒子，水依旧能推草。

当前喷流有下落弧线与有限宽度，并非单条直线。若要求整个喷头严格只有一次直线 query，需要另改喷流与土壤覆盖模型；本次不扩展成这项工作。中心线通过也不能允许水束宽核跨墙。

当前实现结论接入要求
草从支撑土壤读 0–3 湿度，并暗化颜色。并没有逐草 voxel 的叶面水状态。新增每株叶面 wetness；保留土壤水分与生长。两种暗化不简单连乘。
草、苹果读共享 XZ 摆动场，网格输入 Y=0。风可以这样近似，局部喷水不行。个体局部状态；同 XZ 不同高度的苹果分别命中。
草实例 8 bytes，列表可原子 append／重建。绘制下标不是稳定身份。sidecar 按根位置与生命周期重映射；移除重种不能继承旧水。
已有解析阻尼求解与苹果摆长几何。能复用数学与形变，不必新增刚体。现有参数 force 实际是平衡位移，不能直接塞 Newton 数值。
叶响应目前细到渲染 voxel/元素。“一个叶状态”不一定是一片生物叶。优先按小叶簇锚点共享湿度；不再复制完整逐 voxel 水状态。
植物响应在前，喷流准备在后；后者混合了光学采样。不是加一个输入 binding 就能读当帧水流。分开早期 transport 与晚期光学修饰，保证 frame-slot 同步。
掉果使用已发布姿态与异步稀疏读回。新摆动不能只存在于视觉顶点里。位置、速度、阴影与掉果交接读同一最终结果。

一份湿润记忆，一份局部运动。

慢变化：叶面附着水

dw/dt = a · Q · (1 − w) − b · w

接水增加、饱和有上限、停水慢慢干。使用世界时间和解析衰减，避免帧率越高越湿。w 是艺术化的附着水代理，不宣称是真实守恒水库。

快变化：局部冲击与恢复

m(w) q″ + c(w) q′ + k(q − q_rest(w)) = F_spray

水流产生方向明确的作用，正阻尼让运动停止。湿重修改静态下垂与局部喷击恢复；相向输入的合力与积湿量分别累计。

V1 不重写已有环境风系统。“湿重”先由下垂和局部恢复变慢表达，不是声称整株草的全部风响应都已随质量重算。若要湿度同时改变风振动频率，需要每株连续相位或统一受力求解，必须另计成本，不能用 sin(time × frequency(w)) 造成相位跳变。

稳定状态还需要遵守哪些契约？
  • LOD、相机剔除和列表重排不改变湿度；重种视为新生命。
  • 离屏不停止物理受水；停喷后也不能直接清掉回弹与湿润。
  • 草每株只积分一次，所有层、顶点、缓存消费者读取同一份状态。
  • 世界载入清理 transient 叶面水与运动；土壤存档照旧，不先改存档格式。
  • 湿度与受力不依赖雾强度、可见水滴数量或渲染帧号。
  • V1 喷水不自动打落苹果；已有掉果发生时仍需连续交接位置和速度。

省的是重复接触计算，不是宣称“只有一个 float”。

下面以 100,000 株草为算例，不是当前花园的测量数量，也不是最终 GPU ABI。

0.38 MiB

单份、每株一个 f32 湿度

能记住湿润，不能独立表达冲击后的回弹。

3.05 MiB

单份、按 32 bytes 紧凑状态估算

湿润 + 二维局部偏转/速度与对齐余量。索引与输入另算。

24 MiB

若采用六份输出与二次幂容量

131,072 容量 × 32 bytes × 6。提醒：帧槽和历史不是免费，不承诺必须这样分配。

避免采用
每草 voxel × 全部喷头 × 全部水样本水束共享准备；每个接收者只查局部候选
给每株复制现有完整 112-byte 响应结构专门的紧凑局部状态；不复制无用的四份风姿态
每帧 CPU 遍历/读回所有植物GPU 更新与渲染；CPU 只管理布局变化和已有掉果事件
只更新屏幕可见植物，或低频更新漏掉短脉冲按实际受水范围调度；降频时仍积算世界时间内的输入
新增反馈顺便把全部土壤 voxel 水分删掉土壤迁移、生长与存档照旧；叶面水只表达叶面状态

当前没有增量耗时结论。局部候选数在重叠喷头下仍会增长；状态迁移也可能有尖峰。必须测 Release 的 CPU/GPU p50、p95、显存与重建峰值，不能把“小公式”或单元测试当性能证据。

怎么落地，以及什么算真正完成。

共享输入先正确

早期 transport 发布受力输入；不改变原土壤入水。terrain 全墙、半墙、薄墙测试先过。

状态跟对象，不跟绘制顺序

草 sidecar、苹果个体运动、叶簇湿度；重排、重种、世界替换与离屏测试。

接入所有可见消费者

cached/native、pixelized、阴影和掉果交接一致；根固定、摆长固定。

先看效果，再收性能

游戏 Debug 提供保存的运行时 A/B，未勾选是原模式。视觉确认后做独立性能接受，不以小回退阻塞候选展示。

必须验证的代表场景

  • 无风喷水、扫过回弹、停水后仍湿但逐渐静止。
  • 同 XZ 不同高度的苹果，只推动实际命中的那颗。
  • 相向双喷头：力相消，积湿不相消。
  • terrain 后无水；植物后可以有水。
  • 雾强度为零、隐藏粒子，不关闭水的作用。
  • 30/60/120 Hz、暂停、长帧，累积输入一致。
  • 密草、多树、重叠喷头的 Release 配对测量。
  • Vulkan 同步无错误，用户保存设置不被覆盖。
“drippy”还剩一个体验选择。推荐 V1 先做 droopy：湿重下垂 + 回弹。如果也要肉眼看见叶尖滴水，可追加限量视觉水珠；不让每片叶子变成新流体发射器，也不重复计算灌溉。这里没有替你默认加入滴水。
